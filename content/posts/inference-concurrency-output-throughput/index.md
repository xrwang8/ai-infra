同一个模型服务，并发从 1 提高到 8 后，单个请求首 Token 之后的生成间隔中位数从 2.49 ms 增加到 9.07 ms，整轮输出吞吐却从 282 增加到 571 Token/s。并发提高后，更多请求的计算可以一起组织，服务每秒完成的输出总量可能增加。每条请求获得的资源、等待时间和完成时间也随之变化。

这个现象需要同时看三个对象。客户端有多少请求在途，服务端每一步实际选择了哪些请求，整个测试窗口总共交付了多少 Token。以下用一组已有的 8 卡 H100 实测建立这三个视角，再说明如何比较用户体验和服务容量。

## 先看一次并发阶梯实验

被测服务为 DeepSeek-V4.1-Flash-1017，SGLang 0.5.22，8 张 H100 80 GB，TP=8、EP=8，启用 DSpark。客户端采用闭环，固定输入 8,192 Token、目标输出 1,024 Token，结束一个请求后再补发下一个。客户端直连服务，测试期间实例还承接背景业务流量。下表来自关闭性能采集的初测，首 Token 时间和 TPOT 均为请求级百分位，吞吐为整轮输出量除以整轮墙钟时间。

| 客户端并发 | 完成请求 | 整轮输出吞吐 | TTFT P50 / P95 | TPOT P50 / P95 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 8/8 | 282 Token/s | 0.67 / 1.14 s | 2.49 / 4.25 ms |
| 8 | 48/48 | 571 Token/s | 3.54 / 6.96 s | 9.07 / 17.94 ms |
| 16 | 80/80 | 642 Token/s | 14.37 / 18.07 s | 9.14 / 14.41 ms |
| 32 | 160/160 | 676 Token/s | 37.28 / 42.29 s | 8.09 / 14.75 ms |

并发 1 只有 8 条请求，百分位对个别请求十分敏感。表中的并发是客户端在途上限，服务的运行数和排队数需要单独观察。测试使用合成输入与固定输出长度，数据描述当时的负载、实例和背景条件。 [完整 H100 诊断]({{< relref "posts/sglang-h100-prefill-profiling/index.md" >}})

## 先定义三个时间和两个速度

TTFT 从客户端发出请求计到收到第一个含新增 Token 的流式事件。它覆盖输入处理、排队、Prefill、首个输出产生与交付。TPOT 在这份测试中使用请求的首、末输出 Token 时间，计算：

```text
请求 TPOT = (最后输出 Token 时间 − 首次输出 Token 时间) / (输出 Token 数 − 1)
```

如果某请求输出了 1,024 个 Token，首个 Token 在 4 秒到达，最后一个在 14 秒到达，TPOT 约为 `10 / 1023 = 9.78 ms/Token`。首个 Token 之前的 4 秒不会出现在这个 TPOT 里。单请求完整耗时约 14 秒，期间包括首段等待。

整轮输出吞吐的分母是整个测试窗口。比如一轮实际交付 49,152 个输出 Token，用时 86 秒，整轮吞吐约为 `49,152 / 86 = 571.5 Token/s`。这里的 86 秒是说明算法的示例，实际测试应使用记录中的起止时间和输出数量。

一次流事件可能带多个 Token，不能简单把相邻 SSE 消息间隔叫作单 Token 计算耗时。报告中的 TPOT 是按输出 Token 数分摊的客户端交付指标。分位数先按每个请求计算，再在这一轮的请求中汇总。 [SGLang 基准测试与指标](https://github.com/sgl-project/sglang/blob/v0.5.22/docs/docs/developer_guide/benchmark_and_profiling.mdx)

## 多个请求如何让设备完成更多工作

自回归生成每一轮都要根据当前状态得到后续 Token。一个请求进入 Decode 时，这一轮可用的输入行数较少。多个可运行请求同时进入时，运行时可以把它们组织到同一批计算中，减少每个请求各自重复承担的一部分模型权重读取、内核启动和调度成本。矩阵形状增大后，设备也可能获得更好的并行度。

用一个简化账本看，假设某个 Decode 步处理 1 个请求用 4 ms，处理 8 个请求用 12 ms，而且每个请求都新增 1 个有效 Token。那么第一种每秒约完成 250 个 Token，第二种约完成 667 个。第二种每个请求等待下一步的时间更长，整批每秒完成的 Token 数也更多。这是说明批处理摊销的假设，实际服务还受算子、上下文、KV Cache、通信和请求分布影响。

连续批处理使一批请求可以在不同时间进入或退出。短请求完成后，新的可运行请求可以填入，不必等待最早一批所有请求全部结束。真正的运行 batch 大小由服务端调度、可用缓存、当前请求阶段以及配置决定。客户端并发 32，只说明客户端最多有 32 个请求同时未完成，不能证明 GPU 每一步都有 32 个请求在做 Decode。

本次服务还使用投机解码。一次 Draft / Verify 可能提交多个被接受的 Token，各轮接受数也会变化。因此“每一步每个请求恰好产生一个 Token”只是上面的解释模型。衡量本次服务的有效产出，应以实际返回的输出 Token 数为准。

## 为什么不能用并发乘单请求速度

并发 8 时 TPOT P50 为 9.07 ms，倒数约为 110 Token/s。这是**先算每个请求的 TPOT，再对请求取中位数后求倒数**得到的参考值，主要描述首个和最后一个输出之间的节奏。将 110 乘以 8 得到 880，并不等于实测的 571。

原因在于分母不同。一个请求的 TPOT 排除了首 Token 等待，整轮墙钟还覆盖 Prefill、入队、请求补位和尾部收尾。不同请求未必在同一时刻开始和结束，运行中的请求数也不断变化。中位数是位置统计量，不能用它直接还原整组请求的累计输出与共同时间。

并发 1 时同样如此。`1000 / 2.49` 约为 402 Token/s，它不是整轮 282 Token/s 的复算结果。前者描述一个请求生成阶段的中位间隔，后者包含这个请求开始输出前的时间。两者配合才能回答“开始后输出多快”和“整个服务窗口完成了多少”。

## 吞吐什么时候开始变平

初测从并发 8 到 32，客户端上限提高了 4 倍，整轮吞吐只从 571 提高到 676 Token/s，增加约 18.4%。同时 TTFT P50 从 3.54 秒上升到 37.28 秒。并发 32 的采样中，运行请求峰值为 10，排队峰值为 31。两个峰值分别在各自采样点出现，不能假定它们必然同时发生。

为什么排队会影响首 Token？本次每个 Prefill chunk 的新 Token 预算为 4,096。一个 8,192 Token 的冷输入包含约两个满块的新输入工作，一个批次也可以把预算分给不同请求。多个长输入进入后，后来的请求要等待准入和输入推进。服务同时处理 Prefill 与 Decode 的方式、其他业务流量和每个请求的状态都会影响等待。

一个常用关系是 `在途请求数 ≈ 完成速率 × 平均停留时间`。它描述稳定窗口中的平均量，要求使用一致的边界和单位。闭环测试增加客户端槽位后，如果完成速率增幅变小，而平均在途数上升，平均停留时间就会增长。一次有限长度测试不必严格达到稳态，但这个关系可以帮助读懂队列：更多在途请求可能只是等得更久。

## 三轮复测为什么比一条曲线更重要

为了检查吞吐增益，测试按 8→16、16→8、8→16 的顺序交替运行，每档每轮 48 条，输入和输出仍为 8K / 1K。

| 复测区块 | 并发 8 输出吞吐 | 并发 16 输出吞吐 | 并发 8 TTFT P95 | 并发 16 TTFT P95 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 508.19 | 532.61 Token/s | 7.69 s | 25.26 s |
| 2 | 567.96 | 528.87 Token/s | 7.37 s | 22.15 s |
| 3 | 614.75 | 616.87 Token/s | 9.10 s | 20.35 s |

三次对照中，并发 16 的吞吐变化分别约为 +4.8%、−6.9%、+0.3%。这说明初测里的 8 到 16 吞吐增益没有在三轮中稳定复现。三个区块的 TTFT P95 则都随并发提高而上升。实例存在背景业务，访问记录数量只能说明测试期间有其他请求，无法用来精确扣除它们的 GPU 负载。

从这组实验可以描述出一个容量拐点附近的现象：客户端继续增加并发时，新增吞吐在波动范围内已经很小，等待首 Token 的尾部却明显增加。它不能单独确定所有输入长度下的最佳并发，也不能作为无背景流量时的容量上限。

## 面向用户体验，怎样同时看吞吐

若交互要求首段在 10 秒内到达，单看输出 Token/s 会漏掉许多等待过长的请求。可以给每个请求定义达标条件，例如 TTFT 不超过 10 秒且请求成功，然后按相同窗口计算：

```text
达标输出速率 = 达标请求实际输出 Token 总数 / 测试窗口墙钟时间
```

这个指标依赖业务自行确定的门槛，门槛不同，结果也不同。若还要求生成过程流畅，需要同时约束 TPOT 或可见内容间隔。测试应保留每个请求的状态、实际输出量、TTFT 和生成阶段计时，再逐条判断。仅有 P95 或整轮吞吐，无法倒推出准确的达标输出速率。

评估时还应固定输入输出分布、缓存状态、到达方式和背景负载。闭环测试中的客户端会等待请求完成后才补位；固定到达率测试则需要持续记录实际到达、完成和积压。两种测试都能回答问题，但它们施加的压力模型不同。对长输入与短输入混跑，还要分别观察 Prefill 排队与 Decode 交付，而不是只看一个全局平均数。

总吞吐提高说明共同窗口内交付了更多 Token。选用哪个并发，需要同时看它给用户带来的首段等待、生成间隔以及这些数字在多轮对照中的稳定性。
