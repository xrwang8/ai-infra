![两段不同长度的序列共享同一组缓存块，无文字封面](images/cover-comic.png)

对比 Qwen3.5-9B 的两份双卡启动日志时，有三行数字很扎眼。KV Cache 显存都显示 **10.8 GiB**，上下文从 8,192 放到 262,144 后，`GPU KV cache size` 却从 **498,594** 变成 **697,834 Token**，约涨 40%。下面一行最大并发又从 **60.86** 掉到 **2.66**。顺着源码把两份日志换回块，得到的都是 **1,339 块**。

## 先保存两次启动的原始输出 {#一先把两行日志拆开看}

两份日志来自同一台机器、两次独立启动。两张 RTX 4090 D，单卡标称 24 GiB，vLLM 0.33.0、BF16、TP=2，模型和镜像一致。两次最多同时跑 8 条序列，每步 2,048 Token，显存利用目标 0.90。第一份显式设 8,192 上下文，第二份移除限制后启动解析到 262,144。这里对比的是两次启动估算，未独立测量其他进程的显存波动。

![两次启动的日志容量与参考满长并发](images/01-startup-logs.png)

图一｜真实启动日志。纵轴是每次启动用于估算的参考长度。两次 Rank 0 的可用缓存显存均显示为 10.8 GiB，日志只保留一位小数；最大并发保留两位小数。

三个数字分别回答三个问题。可用显存给出 Worker 在启动时估出的缓存预算。最大并发回答：如果每条请求都长到当前配置上限，缓存池大致能容下几条？最后，日志里的 Token 容量把这个请求数乘回参考长度。这里的上限包含输入和输出，同一列不能既填满输入，再额外附送一段输出。分子是块池规模，分母是满长请求的用块量；换一个参考长度，相当于换一种计量单位。

第一眼的 10.8 GiB 只保留了一位小数。60.86 也已经舍入，拿它乘回 8,192 对不上整数是正常的。复算时我用日志里的整数 Token 容量来反推，保留取整带来的范围。

## 数缓存组和每组的页 {#二为什么一条序列要付两种缓存成本}

翻模型配置，32 层里有 8 层全注意力和 24 层 Gated DeltaNet（GDN）。全注意力的 K、V 随历史位置增加，GDN 用递推状态继续工作。对这次的 align 模式，启动公式给每个 GDN 组预留两个状态块。实际块表还可能有其他位置，换保留策略时要重新算。

vLLM 会把层按缓存规格分组。这台服务对应一个 8 层的全注意力组和三个各有 8 层的 GDN 组。源码按可兼容规格归类，再切成大小一致的组，目的是让不同组能向同一个块池申请编号。每个编号有一组物理存储槽，哪个组拿到它，哪组的层就使用对应槽位。因此，组数决定了同一请求要向池子申领几份块；它不意味着每一个块编号都要为四组同时预留四倍空间。

这里的缓存页也经过对齐。两次日志都显示，全注意力页被设为 528 个 Token，GDN 页填充到相同的字节尺寸。528 描述的是全注意力页能装下多少位置，并不表示一页 GDN 状态对应连续的 528 份键和值。引擎在内存分配上需要统一页尺寸，但不同组写入的数据结构不一样。这就是为什么直接拿一个通用 Transformer 的每 Token 显存公式去除，会漏掉这套模型里的状态块。

按 vLLM 0.33.0 的容量计算路径，全注意力组对参考长度向上取整，一旦最后几个 Token 跨到新页，就得多申请一整块。三个 GDN 组在本例各按两个块计，合计六块。这个重建采用启动日志里的 align 和无投机解码，并且不计额外的预填充检查点块。若改用带额外状态的配置，应回到相应版本和模式重算，不能沿用这六块。

## 用 22 和 503 块反推池子 {#三反算块池两次都得到-1339}

用 N 表示池子的块数，L 是参考上下文长度，R(L) 是达到这个长度要占的块数。复算时先用 N 除以 R(L)，再乘回 L 取整。这里的变量可以直接和两份日志对上。

```text
R(L) = ⌈L / 528⌉ + 6
满长缓存并发 = N / R(L)
日志 Token 容量 = ⌊N × L / R(L)⌋
```

代入第一组，8,192 个 Token 要占 16 个全注意力块，加上六个状态块，共 22 块。代入第二组，262,144 个 Token 要占 497 个全注意力块，加上六个状态块，共 503 块。接下来不用猜 10.8 GiB 后面藏了多少小数，也不用倒推已经舍入的并发。令日志打印的整数为 T，取整意味着真实乘积至少为 T，且严格小于 T 加一。把这个不等式反解到整数块数，两组各自都只剩下 1,339 这一种可能。

![参考请求的全注意力块和 GDN 状态块拆分](images/02-block-accounting.png)

图二｜按版本源码和启动日志重建块数。左右面板使用各自的横轴刻度，均显示单条参考请求的用块量；1,339 是反算值，未直接从运行时导出块表。

把 1,339 代回去，短参考长度得到 60.8636 倍并发和 498,594 个 Token；长参考长度得到 2.6620 倍并发和 697,834 个 Token，和启动日志一致。还可以做一次字节量级核验：该模型全注意力有四个 KV 头，TP=2 时每个 Rank 持有两个，头维度为 256。以 BF16 存储，算上 K、V 两份，一层一页就是 528 × 2 × 256 × 2 × 2 = 1,081,344 字节。按一个编号横跨八个等宽层槽估算，1,339 个编号对应单 Rank 约 10.79 GiB，与日志的显存量级一致。这个量是按页布局估出的池大小；它与启动时的可用字节预算口径有区别，整块分配还可能留下余数。

最关键的是这六个固定块被摊到多少位置上。8,192 时，六块占一条参考请求全部用块的 27.3%，平均一个块只折算出约 372 个 Token。到 262,144 时，六块占比降到 1.2%，平均一个块折算约 521 个 Token。因此同一个池子看起来能装下更多 Token。与此同时，长请求本身需要的块大幅增加，所以能同时装下的满长请求更少。两个数字一起看，才不会把摊薄的固定成本读成显卡多出了一截显存。

## 把线上请求逐条换算成块 {#四线上预算要按请求长度分布算}

如果生产里既有几千 Token 的短对话，又有二十多万 Token 的文档，我会把请求逐条换成页数，再逐条加上状态块。这个静态算式先假设没有共享，实际运行再看请求已经推进的位置、前缀共享、回收和调度预留。

用一个总量相同的算例，把请求形状的影响单独拎出来。假设有八条各 1,024 个 Token 的请求，每条要两页全注意力和六块状态，共要 64 块；同样的 8,192 个 Token 如果是一条请求，只要 22 块。两种分法的全注意力页数都恰好是 16，差的 42 块全来自多出来的七份状态。这个例子没有假设单条请求更省算力，也没有推断哪组跑得更快，它只说明一个租户同时打开很多独立会话时，入口处的 Token 总量和引擎内的缓存压力会出现多大的偏差。

做负载画像时，最好分别记录到达时的输入长度和终止时的输出长度。前者决定请求进来时要写入多少历史，后者会把这份历史继续往后推。已经排队但还没获得缓存的请求、已经进入模型的请求，以及刚刚结束但前缀仍可复用的页面，也要分开看。拿一个时刻的已占块解释过去一分钟的流量，或者把每条请求都按允许的最大输出去算，都很容易把在途占用估错。对这类混合模型，长度直方图如果不带同时活跃的序列数，仍不足以还原显存压力。

边界上还有一层容易忽略的离散性。在同一算式里，8,448 个位置刚好填满 16 页。多加一个 Token，就跨进第 17 页；总用块从 22 变成 23。这一跳让每块折算的 Token 暂时下降。即使拉长参考长度总体有利于摊薄固定成本，日志数字也未必随长度平滑增加。这个例子是算式的推论，没有单独启动第三个配置来测。对平台容量工具来说，这个细节很有用：以整页为单位计算，才能看到连续估算会掩盖的临界点。

60.86 也不能拿来承诺 60 路服务。这里调度器最多允许 8 条序列同时运行；显存还有实际可分配块、引擎保留块和运行时状态要考虑。2.66 同样只说明按满长缓存模型的比例，不告诉你两条满长请求是否能在目标首段时间内返回。另一个独立探测窗口中，确实有一条 262,080 输入加 64 输出的请求完成，但这个单样本只确认边界形状能跑通，无法检验双路满长的延迟。部署时可以先用块预算筛掉装不下的方案，再用固定输入和输出形状的并发对照观察首段延迟、输出间隔和抢占计数。缓存能放下多少与服务能多快交付，需要分别取证。

同一个块池在运行时还会不断回收、复用块编号。排查请求结束后的显存变化时，另看块池和底层张量的生命周期。[vLLM 的 KV Block 释放到了哪一层？]({{< relref "posts/vllm-kv-cache-memory/index.md" >}})

## 容量面板要保留的三组数据 {#五结论监控容量先选对单位}

这次把参考长度放大了 32 倍。块池仍反算为 1,339 块，一条满长请求的预算从 22 涨到 503 块。固定的状态开销摊薄以后，日志折算出的 Token 变多，而池里能装下的满长请求变少。以后比两次启动，我会把参考长度和每条用块一起抄下来。

看板至少留三栏。第一栏放每个 Rank 的缓存字节或块池规模。第二栏按请求长度估用块。第三栏放业务负载的实际延迟和吞吐。短对话、长文档先分别做并发对照，再用混合流量看短请求首段有没有变差。
